A senior database engineer rejects the single migration and rewrites it as a multi-release expand/contract plan: add `login_email`, dual-write from the app, backfill in throttled batches outside a transaction (including the 2k NULL fills), dedupe case-insensitive collisions, CREATE UNIQUE INDEX CONCURRENTLY with disable_ddl_transaction!, add a NOT VALID check then VALIDATE then SET NOT NULL, switch reads, and drop `email` only after no deployed code uses it (ignored_columns first). Every DDL step runs with a short lock_timeout and retries, and they note the UPDATE inside the migration transaction would hold locks the whole time. A competent generalist usually spots the index-locking problem and suggests batching, but misses the rolling-deploy breakage from the rename, the NOT NULL scan/lock, the case-duplicate failure mode, or the lock-queue risk.
